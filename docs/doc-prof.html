PRD — Generador de Contenido Personalizado con Funcionalidades de IA

1. Resumen del producto

Plataforma de publicación donde autores crean contenido (notas y articulos) y lectores se suscriben a los creadores que les interesan. La IA se integra en dos frentes: como asistente del autor durante todo el ciclo de creación (antes, durante y después de escribir) y como herramienta de consumo para el lector (resumen). Un motor de recomendación determinista personaliza el feed sin depender de IA generativa para esa función.

2. Objetivo

Demostrar un flujo de trabajo real de integración de IA en un producto, con arquitectura backend limpia, sin caer en "IA por moda": cada función de IA resuelve un problema concreto del autor o del lector, y donde una solución determinista es suficiente, se usa esa en vez de gastar recursos de IA innecesariamente.

3. Stack tecnológico

Capa Tecnología Por qué
Backend NestJS (TypeScript) Arquitectura modular por dominio, fácil de aislar la lógica de IA en su propio módulo
Frontend Next.js (App Router) + Tailwind CSS Renderizado híbrido, mobile-first, sin necesidad de infraestructura extra
Base de datos PostgreSQL Relaciones claras entre usuarios, posts, tags y suscripciones; soporta bien las consultas de scoring

4. Funcionalidades core (sin IA)

4.1 Plataforma UGC de suscripción

  • Cualquier usuario puede publicar contenido (User Generated Content)
  • Los lectores siguen autores y/o se suscriben a boletines específicos
  • Feed organizado cronológicamente o por categoría/tag

4.2 Motor de recomendaciones por scoring de tags (sin IA)

Cuando un lector ve un artículo o entra al feed, el sistema calcula qué tan relevante es cada post disponible comparando sus tags contra el historial de lectura del usuario (tabla reading_history). Cuantos más tags en común tenga un artículo con lo que el usuario ya leyó, más arriba aparece en las sugerencias.

Por qué NO usar IA generativa para esto:
Una recomendación de contenido es fundamentalmente un problema de similitud/ranking, no de generación de texto. Pedirle a un modelo de lenguaje "qué artículo le recomendarías a este usuario" es:
  • Más lento: una llamada a la API por cada carga de feed, en vez de una consulta SQL de milisegundos
  • Más caro: cada recomendación consumiría tokens, sin necesidad real
  • Menos confiable: el modelo podría "inventar" relaciones entre artículos que no existen (alucinación), mientras que un match de tags es 100% explicable y predecible
  • Innecesario: el problema ya tiene una solución estándar y barata (recommender systems basados en similitud de atributos), la IA generativa no aporta ventaja aquí
Se reserva la IA para tareas donde sí agrega valor real: generar texto, entender contenido no estructurado, o tomar decisiones de juicio (como moderación). Esto también es un punto fuerte para la sustentación: muestra criterio técnico, no solo "meterle IA a todo".

5. Funcionalidades de IA — Autor

Se diseñaron para acompañar las tres etapas naturales del proceso de escritura, de modo que la IA no sea un botón aislado sino parte del flujo.

5.1 Antes de escribir — Outline Generator

Qué hace: el autor ingresa un tema o idea preliminar; la IA devuelve un esqueleto estructurado en JSON con subtítulos lógicos (H2/H3).

Por qué: resuelve el problema de la "hoja en blanco", que es la principal fricción para publicar contenido nuevo. Al pedir salida en JSON estructurado (no texto libre), se puede renderizar directamente como plantilla editable en el editor.

5.2 Durante la escritura — Títulos + Tono

Qué hace: analiza el borrador y sugiere títulos más atractivos; un control adicional permite regenerar el texto con distinto tono (informal / formal / estilo investigación).

Por qué: el título es el mayor factor de alcance en plataformas de contenido, y el tono permite que el mismo autor sirva a audiencias distintas sin reescribir manualmente. Ambas funciones comparten el mismo endpoint con un parámetro tone, evitando duplicar lógica.

5.3 Después de escribir — Content Score

Qué hace: analiza el borrador terminado y devuelve un puntaje de calidad más sugerencias accionables (claridad, SEO, engagement) y palabras clave sugeridas.

Por qué: a diferencia del outline (estructura) y el tono (estilo), esta función evalúa el resultado final antes de publicar — cierra el ciclo de asistencia. Las keywords_suggested se reutilizan como candidatos de tags, conectando esta feature con la moderación/auto-tagging sin duplicar trabajo.

5.4 Al publicar — Moderación + Auto-tagging

Qué hace: una sola llamada a la IA al momento de publicar devuelve { is_appropriate, reason, suggested_tags }. Si el contenido es apropiado, se publica con los tags sugeridos (editables por el autor); si no, se rechaza mostrando el motivo o se envía a revisión manual.

Por qué combinarlo en una sola función: moderar y etiquetar requieren el mismo insumo (leer y entender el contenido completo), así que se resuelven con una sola llamada en vez de dos, reduciendo costo y latencia. Además, el etiquetado automático alimenta directamente el motor de recomendaciones determinista (sección 4.2): la IA aporta el dato (los tags), pero la lógica de recomendación en sí sigue siendo barata y explicable.

6. Funcionalidad de IA — Lector

6.1 Resumen automático

Qué hace: un botón en artículos largos genera un resumen breve para que el lector capte la esencia sin leer todo el texto.

Por qué: mejora la experiencia de consumo sin requerir que el autor haga trabajo extra; el resumen se genera una sola vez y se cachea (ver sección 8).

7. Modelo de datos (entidades clave)

Entidad Campos relevantes Propósito
users id, nombre, email, rol Autores y lectores (mismo modelo, distinto rol)
posts id, contenido, status, ai_generated_summary, ai_generated_titles, updated_at Contenido publicado, con resultados de IA cacheados
tags id, nombre Catálogo de temas; relación many-to-many con posts
subscriptions id, follower_id, author_id Relación de seguimiento entre lectores y autores
reading_history user_id, post_id, read_at Base del motor de recomendaciones por tags
Por qué tags como tabla propia y no un array de strings en posts: permite hacer JOINs eficientes para el scoring de recomendaciones y evita duplicar/normalizar strings sueltos.

8. Arquitectura de IA

Toda la lógica de IA vive en un AiModule con un AiService que expone: generateOutline, suggestTitles, adjustTone, analyzeContent, moderateAndTag, summarize. Los módulos de dominio (posts, etc.) inyectan este servicio en vez de llamar directamente a la API externa.

Decisiones de diseño clave

Decisión Por qué
Llamadas siempre desde el backend Nunca exponer la API key en el cliente; también permite aplicar rate limiting y cache de forma centralizada
Rate limiting en endpoints de IA Evita abuso y controla costos de la API externa
Cache de resultados en la fila del post Un resumen o título generado no cambia si el post no se editó; evita llamadas repetidas innecesarias. Se invalida comparando contra updated_at
Fallback si la IA falla El post debe poder publicarse igual (sin tags automáticos, marcado para revisión manual); la disponibilidad del producto no puede depender de un proveedor externo
Moderación asíncrona Evita que el autor espere varios segundos al publicar; el post se guarda como pendiente y se notifica cuando la revisión termina
